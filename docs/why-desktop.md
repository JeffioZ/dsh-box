# 为什么做 DSHBox

## 我们解决什么问题

DeepSeek Harness（dsh）是一个“一切皆插件”的 agent harness。首次运行仍需处理 Node.js、profile、依赖安装、端口和进程生命周期；主要入口是命令行与浏览器。

DSHBox 把同一个运行时放进符合操作系统习惯的桌面应用：

- 提供各平台可直接运行的产物：自动准备 Node.js 与 dsh 运行时；Windows 缺少 WebView2 时引导安装。
- 应用负责窗口、托盘、单实例、自绘菜单与本地服务生命周期（启动、看门狗、退出清理）。
- 用户仍然使用官方 dsh 的 profile、插件、会话与 Web UI，数据与 CLI 用法完全共享。
- 上游 Harness 继续拥有 agent、模型、工具、会话与 Web 界面的核心语义。

DSHBox 的职责是产品入口和运行时适配。上游源码保持独立，官方升级路径不受影响。

## 我们与 dsh 的边界（三条通道）

外壳与 dsh 之间只存在三条受控通道，任何新功能先判断走哪条，走不通就不做：

1. **注入**：向 dsh 页面注入 JS/CSS（右键菜单、主题首帧预设、页面状态观察）。
2. **数据**：读写 `$DSH_HOME`（只读会话日志；行级合并写 `settings.yaml` 的 `locale` / `ui-theme` / `llm-pi-ai` 段与 `.credentials.yaml` 的对应凭据）。
3. **CLI**：调用 `dsh` CLI（`dsh web`、`dsh plugin ...`）。

以下能力超出项目边界：fork 上游源码、patch dsh 包、修改会话格式、向 dsh 内核注册自定义 service。它们会让桌面端脱离官方升级轨道。

## 我们刻意不做什么

- 不重做 dsh 的 Web UI：对话、工具调用、审批、设置页都是官方界面。
- 不做成 IDE：不提供三列工作台、Git Review 面板、内嵌浏览器等"编辑器替代品"。
- 不复制会话数据到第二套数据库：会话统计等能力只读复用官方会话日志。
- 不把 roadmap 写成已交付功能：规划中的能力（远程控制、IM 通道等）在发布说明与 README 中如实标注状态。
- 不向页面暴露 Tauri/Electron 级私有能力：页面能用的只有我们明确注入的菜单与事件。

## 设计取舍

- **Tauri v2 而非 Electron**：单文件分发、体积与内存更小、系统原生窗口；代价是 WebView2 依赖（缺失时引导安装）与较少的桌面生态库。
- **首选端口 + 上次成功端口 + 系统分配**：通常保持稳定 origin，让 dsh 前端偏好可持久记住；遇到占用或 Windows 保留段时直接用 `--port 0` 原子分配，不顺序扫描大段相邻端口。代价是极端冲突场景下 origin 会变化，dsh 页面保存在 origin 下的当前会话选择会回到默认。
- **外部 dsh 明确接入而非自动接管**：发现官方默认端口 `3080` 或首选端口上的 dsh 时，通过页面与 RPC 双重校验，再让用户选择。外部模式不会停止、更新或写入其配置；代价是上游尚未暴露 `DSH_HOME`/实例 ID，首次连接仍需人工确认，且外部服务的管理操作要回到原环境完成。
- **内置 Node/dsh 与复用本机 Node 结合**：系统已有满足版本要求的 Node 直接复用；否则安装应用自带的运行时，不污染用户全局环境。
- **更新事务化**：dsh/Node 更新遵循"备份 → 标记 → 替换 → 校验 → 回滚"原语，打断后下次启动自动还原，不会把运行时弄坏。
- **不引入前端构建链**：内置页维持原生 HTML/CSS/JS，启动和分发简单；代价是共享组件与类型检查能力有限，所以用项目一致性脚本补齐语法、i18n、链接和注入契约检查。
- **保留原生右键能力**：不照搬参考项目的页面级简化菜单；本地文件菜单继续提供默认打开、编辑器打开、定位、复制路径/内容等高频能力，只对异步竞态、路径解析和危险默认打开做收敛。

## 适合谁

- 想安装后直接使用 Harness 的用户：从 README「快速开始」开始。
- 想了解启动、运行时管理与打包边界的维护者：阅读 README「项目结构」与 AGENTS.md。
- 想扩展桌面能力的开发者：优先考虑 dsh 插件生态（外壳不提供私有扩展 API）。
