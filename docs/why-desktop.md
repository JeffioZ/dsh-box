# 为什么做 DSHDesktop

## 我们解决什么问题

DeepSeek Harness（dsh）是一个"一切皆插件"的 agent harness，功能完整，但第一次运行仍然要面对 Node.js、profile、依赖安装、端口和进程生命周期。命令行与浏览器是它的主场，不是普通桌面用户熟悉的形态。

DSHDesktop 的目标不是重新实现 Harness，而是把同一个运行时放进一个符合操作系统习惯的应用里：

- 单个 exe，双击即用：自动准备 WebView2、Node.js 与 dsh 运行时。
- 应用负责窗口、托盘、单实例、自绘菜单与本地服务生命周期（启动、看门狗、退出清理）。
- 用户仍然使用官方 dsh 的 profile、插件、会话与 Web UI，数据与 CLI 用法完全共享。
- 上游 Harness 继续拥有 agent、模型、工具、会话与 Web 界面的核心语义。

因此 DSHDesktop 是一个**产品入口与运行时适配层**：不替代上游，不复制一份上游源码长期分叉。

## 我们与 dsh 的边界（三条通道）

外壳与 dsh 之间只存在三条受控通道，任何新功能先判断走哪条，走不通就不做：

1. **注入**：向 dsh 页面注入 JS/CSS（右键菜单、主题首帧预设、页面状态观察）。
2. **数据**：读写 `$DSH_HOME`（只读会话日志；行级合并写 `settings.yaml` 的 `locale` / `ui-theme` 段）。
3. **CLI**：调用 `dsh` CLI（`dsh web`、`dsh plugin ...`）。

**不做的**：fork 上游源码、patch dsh 包、修改会话格式、向 dsh 内核注册自定义 service。这会让我们脱离官方升级轨道，是长期维护成本最高的一条路。

## 我们刻意不做什么

- 不重做 dsh 的 Web UI：对话、工具调用、审批、设置页都是官方界面。
- 不做成 IDE：不提供三列工作台、Git Review 面板、内嵌浏览器等"编辑器替代品"。
- 不复制会话数据到第二套数据库：文件变更追踪等能力只读复用官方会话日志。
- 不把 roadmap 写成已交付功能：规划中的能力（远程控制、IM 通道、插件市场等）在发布说明与 README 中如实标注状态。
- 不向页面暴露 Tauri/Electron 级私有能力：页面能用的只有我们明确注入的菜单与事件。

## 设计取舍

- **Tauri v2 而非 Electron**：单文件分发、体积与内存更小、系统原生窗口；代价是 WebView2 依赖（缺失时引导安装）与较少的桌面生态库。
- **固定端口 3080（冲突时回退）而非随机端口**：稳定 origin 让 dsh 前端的会话分组等界面偏好可以持久记住。
- **内置 Node/dsh 与复用本机 Node 结合**：系统已有满足版本要求的 Node 直接复用；否则安装应用自带的运行时，不污染用户全局环境。
- **更新事务化**：dsh/Node 更新遵循"备份 → 标记 → 替换 → 校验 → 回滚"原语，打断后下次启动自动还原，不会把运行时弄坏。

## 适合谁

- 想安装后直接使用 Harness 的用户：从 README「快速开始」开始。
- 想了解启动、运行时管理与打包边界的维护者：阅读 README「项目结构」与 AGENTS.md。
- 想扩展桌面能力的开发者：优先考虑 dsh 插件生态（外壳不提供私有扩展 API）。
